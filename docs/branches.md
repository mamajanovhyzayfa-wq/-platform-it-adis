# Филиалы ITadis

Платформа — один код и одна инфраструктура, но каждый филиал работает со своей
PostgreSQL, своим каталогом файлов и своими пользователями. Данные филиалов
физически не пересекаются.

## Как определяется филиал

1. Express-middleware читает **только `Host`** запроса (без порта, в нижнем регистре).
2. Домен ищется в управляющей таблице `Branch`. Кеш — 30 секунд, сбрасывается при
   создании и активации филиала.
3. Если домен принадлежит неактивированному филиалу — ответ `404 BRANCH_NOT_ACTIVE`.
   Основная БД в этом случае не подставляется.
4. Неизвестный домен в development может обслуживаться основным филиалом
   (`ALLOW_PRIMARY_FALLBACK=true`). В production fallback выключен по умолчанию:
   неизвестный домен получает `404 BRANCH_NOT_FOUND`. Основной домен задаётся
   через `PRIMARY_DOMAIN` и привязывается к записи `isPrimary` при старте API.
5. Для найденного филиала создаётся `TenantContext` (AsyncLocalStorage) с отдельным
   `PrismaClient`, каталогом вложений и `branchId`.

Ни URL, ни query, ни тело запроса не участвуют в выборе филиала. Идентификатор
филиала нельзя подменить клиентским параметром.

## Изоляция данных

- **База данных.** У каждого филиала своя БД (`itadis_branch_<slug>`). Prisma-прокси
  (`src/lib/prisma.ts`) направляет все обращения доменного кода в БД текущего
  филиала; вне запроса используется основная БД.
- **Пользователи и сессии.** Пользователь существует только в БД своего филиала.
  Один и тот же email может быть администратором в двух филиалах — это две разные
  учётные записи, как и требует архитектура. Наставник заводится в каждом филиале
  отдельно.
- **Токены.** Access-токен содержит `branchId`. Guard и общий middleware отклоняют
  токен, выданный в другом филиале (`403 FOREIGN_BRANCH_TOKEN`), и старые токены без
  `branchId` вне основного филиала. Refresh-сессии лежат в БД филиала, поэтому
  refresh с чужого домена возвращает `401`.
- **Файлы.** Загрузки пишутся в `uploads/branches/<slug>`, статика `/uploads`
  отдаётся только из каталога текущего филиала. Файл одного филиала по домену
  другого недоступен.
- **Управляющая БД.** Таблица `Branch` хранит только реестр: имя, домен, имя БД,
  префикс хранилища, статус, шаги, email администратора и конфигурация. Паролей БД
  и паролей пользователей там нет.
- **Realtime и фоновые задачи.** Socket.IO определяет филиал по Host рукопожатия и
  кладёт branchId в имена комнат; цикл напоминаний о занятиях обходит активные
  филиалы и выполняет запросы в БД каждого из них.

## Создание филиала

Доступно только главному администратору ITadis. Консоль — `/platform` в admin-web,
API — `/api/platform/*` с отдельным токеном (`scope: platform`). Этот токен не даёт
доступа к студентам, платежам и учебным данным филиалов.

`POST /api/platform/branches`

```json
{
  "name": "Филиал Ош",
  "domain": "osh.itadis.kg",
  "slug": "osh",
  "adminEmail": "admin@osh.itadis.kg",
  "adminName": "Айгуль Осмонова"
}
```

Шаги выполняются последовательно и сохраняются в `Branch.steps`:

1. Проверка формата и уникальности домена.
2. `CREATE DATABASE "itadis_branch_<slug>"` от имени пользователя `DATABASE_URL`
   (нужно право `CREATEDB`).
3. Применение всех `prisma/migrations/*/migration.sql`; учёт — в таблице
   `_branch_migrations` самой БД филиала.
4. Начальная конфигурация: роли, права, администратор филиала с временным паролем,
   нулевой баланс IT Coins.
5. Отдельный каталог файлов и проверка записи в uploads и библиотеку
   (локальный диск или S3-префикс `branches/<slug>/library`).
6. Health-check: `SELECT 1`, наличие схемы (таблиц), Redis (если настроен),
   параметры безопасности.
7. Начальная конфигурация: `BranchSettings`, лимиты IT Coins, AI-настройки и
   базовая академическая шкала.
8. Статус `PROVISIONED` и результат со списком шагов и временным паролем
   (показывается один раз).

`POST /api/platform/branches/:id/activate` с телом `{ "confirm": true }` повторно
проверяет БД и хранилище и переводит филиал в `ACTIVE`. Без подтверждения — `400`.
Консоль показывает результат и запрашивает подтверждение перед активацией.

Ошибка на любом шаге переводит филиал в `FAILED`, сохраняет `lastError` и шаги;
основная БД при этом не затрагивается.

`POST /api/platform/branches/:id/retry` повторяет провижининг только для
`FAILED`-филиала: недоступная БД пересоздаётся с нуля (поэтому частично
применённая миграция не блокирует повтор), администратор создаётся заново и
получает новый временный пароль. Консоль показывает кнопку «Повторить».
Пересоздаётся только БД неактивного филиала; активные филиалы не затрагиваются.

## Публичные страницы и кабинеты

- Основной домен ITadis (`PRIMARY_DOMAIN`) отдаёт презентационный сайт `/`.
- На домене филиала `/` автоматически открывает `/app/login` (в отдельной
  сборке кабинета — `/login`). Страница входа показывает название, логотип,
  описание, контакты и направления филиала из `Branch.config`; данные определяются
  только по `Host`.
- После входа пользователь попадает в свой кабинет: `/app/admin`, `/app/manager`,
  `/app/mentor`, `/app/student` или `/app/parent`. В корне сайта те же адреса
  (`/admin`, `/manager`, `/mentor`, `/student`, `/parent`) перенаправляют в кабинет.
- Переключателя филиалов в кабинете нет: филиал задан доменом, а роли и данные
  проверяются на сервере. При недостатке роли открывается `/forbidden` с формой
  запроса дополнительной роли у администратора филиала.

## Роли и активный интерфейс

В платформе ровно пять ролей: `STUDENT`, `TEACHER` (наставник), `MANAGER`,
`ADMIN`, `PARENT`. Произвольные роли не создаются. Основная роль хранится в
`User.role`; дополнительные роли выдаются только подтверждёнными записями
`UserRoleGrant` (запрос пользователя и решение администратора в разделе
«Доступ и регистрация» → «Роли и родители»).

Клиент передаёт выбранный интерфейс в заголовке `X-Active-Role`. Сервер принимает
его только при наличии подтверждённого гранта в БД текущего филиала; иначе
используется основная роль из access-токена. Поэтому заголовок не даёт новых прав
и не позволяет обойти ограничения роли. Переключатель доступен в боковом меню
только для подтверждённых ролей; навигация, кабинет и запросы строятся по
активной роли.

Ограничения по ролям:

- ученик видит свои курсы, уроки, расписание, задания, тесты, экзамены, оценки,
  библиотеку и заметки, IT Coins, магазин, достижения, сертификаты, AI и профиль;
- наставник видит свои группы и учеников, курсы, задания, тесты, экзамены,
  расписание, видеоконференции, сообщения, аналитику, AI и материалы;
- менеджер видит учеников, группы, наставников, расписание, заявки,
  посещаемость, организационные отчёты, коммуникации и аналитику филиала, может
  принимать наличные в кассе; финансовый кабинет и `/reports/finance` ему закрыты;
- администратор управляет филиалом, пользователями, ролями, финансами,
  магазином, IT Coins, настройками, интеграциями, аудитом и резервными копиями;
- родитель видит только подтверждённых детей: расписание, посещаемость,
  успеваемость, домашние задания, результаты тестов, IT Coins и историю оплат.

Привязка ребёнка: администратор выдаёт одноразовый код в разделе «Роли и
родители», родитель вводит его на странице «Безопасность», после чего
администратор подтверждает связь. До подтверждения данные ребёнка родителю не
показываются.

## Консоль главного администратора

- Маршрут: `/platform` (вне панели филиала, без его навигации).
- Переменные: `PLATFORM_ADMIN_EMAIL`, `PLATFORM_ADMIN_PASSWORD` или
  `PLATFORM_ADMIN_PASSWORD_HASH`, `PLATFORM_DOMAIN`.
- В production `PLATFORM_DOMAIN` обязателен: без него консоль отключена. Вход и
  API консоли работают только на этом домене; на домене филиала — `403`.
- Консоль показывает реестр филиалов, шаги создания, статус и активацию. Списков
  студентов, платежей и финансов филиалов в ней нет — после активации филиал
  управляется своим администратором.

## Файловое облако и резервное копирование

- У каждого филиала отдельное пространство: S3-префикс
  `branches/{slug}/library` или локальный `STORAGE_DIR/branches/{slug}/library`.
  Ключи объектов строит только сервер; клиент не может выбрать путь или выйти за
  пределы филиала.
- Библиотека доступна через `/api/files`: категории (документы, изображения,
  аудио, видео, PDF, презентации, архивы), поиск, фильтры, сортировка и пагинация.
- Лимит одного файла — до 512 МБ, общая квота задаётся для филиала. Проверяются
  MIME, сигнатуры содержимого, EICAR, исполняемые форматы и внешний антивирус.
  ACL: `PRIVATE` (владелец), `STAFF` (сотрудники), `BRANCH` (филиал); каждое
  скачивание и изменение пишется в `FileAuditLog`.
- Копии БД создаются `pg_dump` в custom-формате, файлов — `tar.gz` из uploads и
  библиотеки. По умолчанию БД копируется каждые 24 часа;
  `backupFrequencyHours`, `backupRetentionDays` и `backupIncludeFiles` задаются
  отдельно для каждого филиала в `/app/backups` (API `/api/backups`).
- Планировщик включается `BACKUP_SCHEDULER_ENABLED=true`; в production compose
  это уже задано. Ручной запуск также сдвигает время следующей автоматической
  копии.
- Целостность проверяется по SHA-256 и структуре: `pg_restore --list` для БД,
  `tar -tzf` для файлов. Ошибка проверки помечает копию `FAILED` и отправляет
  алерт в `ALERT_WEBHOOK_URL`.

### Процедура восстановления

1. **Обнаружение** — администратор создаёт заявку и указывает причину.
2. **Проверка** — выбранные копии БД и файлов пересчитываются и проверяются.
3. **План** — заявка получает статус `PLANNED` и семь шагов процедуры.
4. **Подтверждение** — ответственный вводит пароль (step-up) и точную фразу
   `RESTORE {slug}`; без этого выполнение заблокировано.
5. **Восстановление** — только по заявке в статусе `APPROVED`, атомарно, через
   `pg_restore --clean --if-exists` и распаковку файлов.
6. **Проверка** — подключение к БД, ключевые таблицы и количество файлов.
7. **Отчёт** — статус, проверки и время завершения сохраняются в заявке.

Восстановление никогда не запускается планировщиком. Неудачная проверка или
выполнение остаются в истории со статусом `FAILED` и текстом ошибки.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `CONTROL_DATABASE_URL` | БД реестра; по умолчанию `DATABASE_URL` |
| `ALLOW_PRIMARY_FALLBACK` | `true` только для development; в production `false` |
| `PRIMARY_DOMAIN` | Домен основного филиала; обязателен в production без fallback |
| `BRANCH_DATABASE_PREFIX` | Префикс имён БД, по умолчанию `itadis_branch_` |
| `PLATFORM_DOMAIN` | Домен консоли главного администратора |
| `PLATFORM_ADMIN_EMAIL` | Email главного администратора |
| `PLATFORM_ADMIN_PASSWORD` | Пароль (мин. 8 символов), если не задан хеш |
| `PLATFORM_ADMIN_PASSWORD_HASH` | bcrypt-хеш вместо пароля |
| `BACKUP_DIR` | Каталог локальных копий вне публичной статики |
| `BACKUP_SCHEDULER_ENABLED` | `true` включает автоматические копии; в production compose уже `true` |
| `PG_DUMP_BIN` / `PG_RESTORE_BIN` | Пути к клиенту PostgreSQL, если его нет в `PATH` |
| `S3_ENDPOINT` / `S3_BUCKET` / `S3_ACCESS_KEY` / `S3_SECRET_KEY` | Объектное хранилище библиотеки и копий |

## Проверка изоляции

```bash
# Вход администратора филиала
curl -X POST http://127.0.0.1:4000/api/auth/login \
  -H 'Host: osh.itadis.kg' -H 'Content-Type: application/json' \
  -d '{"identifier":"admin@osh.itadis.kg","password":"..."}'

# Тот же токен на основном домене
curl http://127.0.0.1:4000/api/users/me -H 'Authorization: Bearer <token>'
# 403 FOREIGN_BRANCH_TOKEN
```

## Ограничения и эксплуатация

- Пользователь PostgreSQL должен иметь `CREATEDB`; для резервного копирования —
  отдельные дампы каждой БД филиала.
- Неудачное создание оставляет БД для диагностики; его можно повторить через
  `POST /api/platform/branches/:id/retry`, не создавая новый домен.
- Файлы филиалов лежат на локальном диске. При нескольких инстансах задайте S3
  или общий сетевой том для `uploads` и `STORAGE_DIR`; копии должны попадать в
  `BACKUP_DIR` на постоянном томе или в S3.
- TLS и DNS для доменов филиалов настраиваются на уровне reverse proxy; приложение
  доверяет `Host` только после проверки домена в реестре.
