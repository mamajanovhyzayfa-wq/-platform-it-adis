# Финансовый модуль ITadis

Счета за обучение, платежи, возвраты, расходы, тарифы курсов, заработок наставников,
онлайн-оплата и аналитика филиала.

Код: `apps/api/src/modules/finance`, веб-кабинет: `apps/web/src/pages/finance`,
миграции: `apps/api/prisma/migrations/20261119120000_finance` и
`20261120000000_finance_analytics`.

## Деньги и точность

Все суммы — целые числа в сомах (KGS). Дробной части у сома в расчётах нет,
поэтому `Int` вместо `Decimal`/`Float`: нет ошибок округления, суммы начислений
и частей рассрочки всегда сходятся. Поле `currency` в ответах фиксировано `KGS`.

IT Coins к деньгам отношения не имеют: это отдельная внутренняя валюта
(`CoinBalance`/`CoinTransaction`), она не участвует в оплате обучения и не
попадает в доходы, расходы или прибыль.

## Роли

| Действие | ADMIN | MANAGER | STUDENT | PARENT |
| --- | --- | --- | --- | --- |
| Аналитика, доходы, расходы, прибыль | да | нет | нет | нет |
| Счета: создание, скидки, отмена, все платежи | да | нет | нет | нет |
| Наличный платёж по счёту | да | да (касса) | нет | нет |
| Возвраты: заявка и решение | да | нет | нет | нет |
| Свои счета, квитанции и онлайн-оплата | — | — | да | да, по подтверждённым детям |
| Тарифы, платёжные аккаунты, экспорт | да | нет | нет | нет |

Менеджер видит только незакрытые счета через `GET /api/finance/manager/invoices`:
номер, ученик, назначение, остаток и срок. Аналитика, реестр платежей, расходы,
возвраты и тарифы ему недоступны. В веб-панели для менеджера открыта только
«Касса»; `/finance` и `/reports/finance` закрыты.

Ученик видит только свои счета, родитель — счета детей, у которых
`ParentStudentLink.verifiedAt` заполнен. Проверка выполняется на сервере по
идентификатору из access-токена; параметры запроса на доступ не влияют.

## Модели

- `Invoice` — счёт: `number` (`INV-2026-000001`), ученик, курс, сумма, срок,
  `periodMonth` (`YYYY-MM` для ежемесячной оплаты), статус, автор, причина отмены.
- `InvoiceSequence` — счётчик номеров на год, инкремент в транзакции.
- `Payment` — платёж: сумма, способ (`CASH`, `BANK_TRANSFER`, `ONLINE`), статус,
  провайдер и `externalId`, ключ идемпотентности, кто принял и подтвердил.
- `Refund` — заявка на возврат: платёж, сумма, причина, статус, кто запросил и
  кто рассмотрел.
- `Expense` — расход: категория, сумма, дата, описание, документы, автор.
- `InvoiceDiscount` — ручная скидка с причиной и автором.
- `PaymentAdjustment` — история ручных корректировок суммы/статуса платежа.
- `Course.priceKgs`, `Course.billing`, `Course.installmentsCount` и
  `CoursePriceHistory` — фиксированная цена курса, модель оплаты и история цен.
- `Teacher.lessonRateKgs` — фиксированная ставка наставника за проведённое занятие.
- `PaymentProviderAccount` — аккаунт локального провайдера филиала. Секрет в базе
  не хранится: поле `secretEnvVar` содержит только имя переменной окружения.

## Стоимость курса и счета

Для курса задаётся фиксированная цена и модель оплаты:

- `FULL` — один счёт на полную стоимость;
- `MONTHLY` — счёт на месяц с `periodMonth`;
- `INSTALLMENT` — несколько счетов по графику из `installmentsCount` частей.

Администратор может выставить счёт вручную, выбрать курс (сумма подставляется из
его цены), изменить сумму счёта и применить ручную скидку с обязательной причиной.
Изменение цены курса не пересчитывает уже выставленные счета; история цен
сохраняется отдельно. Индивидуальная цена для каждого ученика не требуется.

Остаток и статус счёта пересчитываются по движениям денег:

- получено = сумма платежей в статусе `CONFIRMED` или `REFUNDED`;
- возвращено = сумма `APPROVED`-возвратов;
- остаток = `max(0, сумма счёта − получено + возвращено)`;
- переплата = `max(0, получено − возвращено − сумма счёта)`.

`OVERDUE` вычисляется при чтении по `dueAt`, поэтому фоновое задание для
просрочки не нужно. Отменённые счета и черновики не пересчитываются.

Возврат нельзя оформить больше, чем осталось по платежу с учётом уже одобренных
возвратов и заявок на рассмотрении. Заявка требует причину, решение принимает
администратор; после одобрения платёж полностью возвращённой суммы получает
статус `REFUNDED`, а счёт пересчитывается. Онлайн-возврат выполняется в кабинете
провайдера: модуль не эмулирует возврат, если у провайдера нет документированного
API возврата.

## Документы

- `GET /api/finance/invoices/:id/receipt` — печатная HTML-квитанция;
- `GET /api/finance/invoices/:id/pdf` — PDF-квитанция, формируется на сервере
  через `pdfkit` со встроенным Unicode-шрифтом DejaVu Sans;
- в счёте есть номер, дата, услуга, сумма, статус, платежи, скидки и остаток.

PDF является внутренней квитанцией об оплате обучения, а не фискальным чеком.
Для фискализации нужен отдельный сервис/касса, подключённый к филиалу. Для
FreedomPay Кыргызстан официальная документация не предусматривает формирование
фискальных чеков через `pg_receipt` (форматы ОФД описаны для Казахстана,
Узбекистана и России), поэтому модуль не отправляет выдуманные фискальные поля.

## Аналитика

`GET /api/finance/overview?from&to` возвращает:

- поступления, возвраты, чистый доход, расходы и прибыль;
- задолженность, просрочку и список должников;
- способы оплаты, расходы по категориям;
- доход по курсам и группы (курс, число активных учеников, поступления, долг);
- динамику за шесть месяцев.

`GET /api/finance/export` отдаёт CSV, `GET /api/finance/accounting` — JSON с
платежами, расходами и возвратами для бухгалтерии. Дополнительно
`POST /api/integrations/accounting/entries` отправляет одну проводку в
настроенный бухгалтерский адаптер.

## Заработок наставников

`GET /api/finance/teacher-earnings?from&to` считает завершённые занятия
(`Schedule.status = COMPLETED`) × фиксированную ставку `Teacher.lessonRateKgs`.
`PATCH /api/finance/teachers/:userId/rate` меняет ставку. Полноценная зарплатная
система, налоги и удержания не реализуются: ТЗ требует только фиксированную ставку.

## Идемпотентность и целостность

- Номер счёта выдаётся внутри транзакции через `InvoiceSequence`.
- Платёж блокирует строку счёта (`SELECT ... FOR UPDATE`) и проверяет остаток в
  той же транзакции: одновременные платежи не создают переплату.
- `idempotencyKey` платежа уникален: повторная отправка возвращает
  `{ duplicate: true }` без второго списания.
- `externalId` платежа уникален: повторный вебхук не создаёт второй платёж.
- Все изменения пишутся в `AuditLog` (`finance.invoice.created`,
  `finance.payment.registered`, `finance.refund.approved`,
  `finance.provider_account.saved` и т.д.).

## Уведомления

Счёт, платёж, скидка и решение по возврату создают `Notification`
(`INVOICE_ISSUED`, `PAYMENT_RECEIVED`, `REFUND_PROCESSED`) ученику и
подтверждённым родителям и отправляют push через `lib/push.ts`.

## Онлайн-платежи

Платёжные секреты не попадают в базу. `PaymentProviderAccount.secretEnvVar`
указывает на переменную окружения сервера. Если аккаунта в базе нет, адаптер
может использовать env-переменные филиала:

```
FREEDOMPAY_MERCHANT_ID
FREEDOMPAY_SECRET_KEY
FREEDOMPAY_BASE_URL
FREEDOMPAY_TESTING_MODE

ELSOM_PARTNER_CODE
ELSOM_PASSWORD
ELSOM_TENANT_ID
ELSOM_BASE_URL
```

Поддерживаются два локальных провайдера, реализованные по официальной
документации:

- **FreedomPay Кыргызстан** — `POST https://api.freedompay.kg/init_payment.php`,
  MD5-подпись `script;отсортированные поля;secret`, Result URL с проверкой
  подписи. Настраивается merchant id, секрет, тестовый режим.
- **Elsom / КИКБ** — `POST {base}/service/v1/merchant/generateOTP/{tenant-id}`,
  запрос статуса `PartnerGetPaymentStatus`, callback `PartnerPaymentResult`.
  Elsom не подписывает callback, поэтому перед подтверждением успеха сервер
  вызывает официальный запрос статуса и принимает только статус `A`.

Callback URL: `/api/finance/webhooks/freedompay` и
`/api/finance/webhooks/elsom`. При нескольких аккаунтах FreedomPay подпись
проверяется по каждому аккаунту, чтобы выбрать правильный секрет. Сумма
подтверждённого онлайн-платежа сверяется с созданным платежом и остатком счёта.
Если вебхук не подтверждён подписью (FreedomPay) или официальным статусом
(Elsom), платёж не зачисляется.

## Ограничения

- Фискализация (чек налогового сервиса) не подключена. Внутренняя PDF-квитанция
  не заменяет фискальный чек.
- Возврат онлайн-платежа оформляется в кабинете провайдера, если у него нет
  документированного API возврата; в системе фиксируется только возврат
  наличного/банковского платежа.
- Для реальных платежей нужны merchant-реквизиты и тестовый контур провайдера.
  Без них проверяются только подпись, разбор ответов и сценарии ошибок.
